# Imrane work management

Resolve the requested registered lane using the workspace router and read its minimum context. Shared system work uses governance. Keep each client's work records and evidence in that lane; the shared library contains methods, not client facts.

For a tiny correction or answer, work directly with an appropriate check. Otherwise choose light mode for a clear small deliverable, standard for research/dependencies/material uncertainty. Reuse information already supplied. Ask only missing questions that change the result; tailor a client questionnaire to this assignment.

Read [the working guide](resources/START_HERE.md) for stages and CLI use. Use [the brief shape](resources/templates/brief.example.json) when creating a record with this skill's `scripts/imrane-work.py` (resolve its absolute path from this SKILL.md). Supply explicit workspace and project. JSON input files and artifacts must belong to the selected lane. Updates replace supplied nested objects and arrays; preserve existing useful entries. Work records supplement the four canonical memories.

Organize qualification, research, plan, production, review, delivery and follow-up at the level the task needs. Light work may skip research/plan. A stage is not authorization for an external action. Continue authorized reversible work without asking for repeated permission. Use relevant domain skills only; do not run every marketing framework for a targeted request.

Before delivery, compare the actual result with its acceptance criteria. Use relevant [domain checks](resources/DOMAIN_CHECKS.md). Attach observed/measured evidence with source and date; reported claims, hypotheses and unknowns are not passed outcome evidence. Inspect the evidence itself: mechanical validation cannot establish truth, review independence or lesson sanitization. Consequential work needs an independent reviewer, proportionate to risk; preserve actual host delegation permissions. Failed checks return to production. A prepared local artifact is not an email sent or a deployment completed.

For planning, generate only the selected lane's board. Explain impact, urgency, effort, blockers and next action. The score is a transparent suggestion, not an automatic choice or productivity claim. Respect owner commitments and surface material tradeoffs.

For choices worth learning from, retain prediction, rationale, test, observation and outcome. Keep unobserved results pending/inconclusive. Turn lessons into contextual drafts with limitations and successful/rejected examples. Export only the selected approved, reviewed, sanitized lesson locally. Cross-lane sharing still follows the workspace handoff policy; never copy client records into shared skills or silently modify a skill from a lesson.

After substantive project work or at requested compaction, update the selected lane's canonical memory and run its existing snapshot procedure. A tiny read-only answer does not require a new work record or memory write. Report real unavailable checks. Do not install dependencies, refresh a network corpus, change host approvals, publish, contact people or spend money solely because this workflow is active.

This is an owner-requested method authored on 2 November 2026 and packaged for portable use in 0.2.1-rc.1. The CLI, Python modules, documentation, templates and synthetic examples are bundled here; no original workspace is required. Both Codex and Claude views receive identical resources. Read [distribution and compatibility](DISTRIBUTION.md) for installation and host limits.
